# Permish — Development Guide

## Project Overview

A cross-platform app that digitizes the LDS Church "Parental or Guardian Permission and Medical Release Form." Event planners create pre-filled events with unique URLs; parents complete, sign, and submit forms. PDFs are generated by filling in the actual official church PDF. Supports web, desktop, and mobile (all via Tauri v2) with offline-first capability.

## Tech Stack

- **Frontend:** SvelteKit (Svelte 5 runes mode) + shadcn-svelte + Tailwind CSS v4
- **Backend:** a single **Bun + Hono + SQLite (`bun:sqlite`)** server in `server/` — one TypeScript process handling routes, auth, PDF, email, and SMS. (There is no longer an Express backend, PocketBase, or Node sidecar; those were consolidated away.)
- **Desktop + Mobile:** Tauri v2 (iOS/Android + desktop from one shell); native SQLite via `@tauri-apps/plugin-sql`. (Capacitor is not used.)
- **Offline:** sql.js (WebAssembly SQLite) with IndexedDB persistence on web; hybrid mode syncs to the server
- **PDF:** pdf-lib (fills actual church PDF form fields) — runs in the server process
- **Email:** Nodemailer (Gmail SMTP default, Resend-ready)
- **SMS:** Carrier email gateways via Nodemailer
- **Auth:** JWT via HttpOnly SameSite=Strict cookies (bcryptjs); the browser talks to the server directly (`credentials: 'include'`), no SvelteKit auth proxy
- **Frontend package manager:** pnpm (NOT npm). **Server:** Bun.
- **Node Version:** 24 LTS (managed via nvm, see .nvmrc)
- **Deployment:** Docker Compose (`server` + `frontend`, optional `caddy` production profile)

## Architecture

### Repository Pattern

The frontend uses a **repository pattern** that decouples all data access from any specific backend. Pages never import backend SDKs directly.

```
Pages/Components → getRepository() → DataRepository interface
                                        ├── HTTP adapter   (thin REST client → Bun server)
                                        ├── Local adapter  (sql.js SQLite, offline)
                                        └── Hybrid adapter (local + background sync to server)
```

**Key files:**
- `frontend/src/lib/data/types.ts` — domain types (User, Event, Submission, etc.)
- `frontend/src/lib/data/repository.ts` — interfaces (AuthRepository, EventRepository, etc.)
- `frontend/src/lib/data/adapters/http.ts` — the single remote adapter (REST client for the Bun server)
- `frontend/src/lib/data/adapters/local.ts` — Offline-first local SQLite adapter
- `frontend/src/lib/data/sync/hybrid.ts` — Hybrid adapter (local + background sync)
- `frontend/src/lib/data/sync/manager.ts` — SyncManager (push/pull changes)
- `frontend/src/lib/data/index.ts` — Provider factory (`initRepository()`, `getRepository()`)

The server lives in `server/` (Bun + Hono). Its routes mirror the `DataRepository`
contract the HTTP adapter calls (`/api/auth`, `/api/events`, `/api/profiles`,
`/api/submissions`, `/api/groups`, `/api/invites`, `/api/admin`).

### Data Modes

Controlled by `localStorage` key `permish_data_mode`:

| Mode | Backend | Behavior |
|---|---|---|
| `online` (default) | Bun server (HTTP adapter) | All data on the server |
| `local` | sql.js (in-browser) | Fully offline, data never leaves device |
| `hybrid` | Local SQLite + sync to Bun server | Works offline, syncs when connected |

There is a single backend (the Bun server), so there is no `PUBLIC_BACKEND` switch.
The server URL comes from `PUBLIC_API_URL` (or the current origin / a user-set
`permish_server_url` in localStorage).

### Backup/Restore

- `BackupManager` at `frontend/src/lib/data/backup/manager.ts`
- Exports local SQLite as `.permish-backup` file
- AES-256-GCM encryption with PBKDF2 key derivation from passphrase
- SHA-256 integrity checking on restore

## Development Commands

```bash
# Start the server (from server/)
bun run dev                 # Bun + Hono on port 3001 (watch mode)

# Start frontend (from frontend/)
pnpm dev                    # runs on port 3000

# Run server tests
bun test                    # from server/

# Build frontend
pnpm build                  # from frontend/

# Desktop + mobile (Tauri v2, requires Rust)
pnpm tauri:dev              # from frontend/
pnpm tauri:build            # from frontend/ (builds distributable)
pnpm tauri:ios             # from frontend/ (iOS)
pnpm tauri:android         # from frontend/ (Android)

# Docker Compose
docker compose up                              # server + frontend
DOMAIN=permish.app docker compose --profile production up  # + Caddy HTTPS
```

## Important Conventions

### Repository Pattern Usage

All pages use `getRepository()` from `$lib/data`:
```typescript
import { getRepository } from '$lib/data';
const repo = getRepository();
const events = await repo.events.list();
```

**Never import `$lib/api` directly** — it exists only as a reference. All data access goes through the repository.

### UI Components

- **Use shadcn-svelte components** for everything. If a component doesn't exist in shadcn-svelte, build it to match shadcn design patterns exactly.
- Components are hand-built in `frontend/src/lib/components/ui/` following exact shadcn patterns.
- All components use **Svelte 5 runes** (`$props()`, `$state()`, `$derived`, `$effect`, `$bindable()`).
- The `cn()` utility at `$lib/utils.ts` merges Tailwind classes.
- Theme colors use CSS variables defined in `app.css` (oklch format with dark mode).

#### Atomic design

The frontend follows atomic design: **atoms** (`components/ui/`, `components/atoms/`) → **molecules** (`components/molecules/`) → **organisms** (`components/organisms/`) → **composables** (`components/composables/`) → **pages** (`routes/**/+page.svelte`). The 3× rule: if a pattern repeats inline in three places, extract it to a molecule before the fourth. Pages orchestrate; they don't render headers, list cards, status pills, or filter bars inline. Before writing any new component, check `btrs/knowledge/conventions/registry.md` — it lists what exists and what's planned. Full rules: `btrs/knowledge/conventions/ui.md`. Anti-patterns: `btrs/knowledge/conventions/anti-patterns.md`.

### Field Name Consistency

Domain types in `frontend/src/lib/data/types.ts` are the single source of truth. Field names match the SQLite schema exactly:

| Correct Name | NOT This |
|---|---|
| participant_name | first_name, last_name |
| participant_dob | date_of_birth |
| participant_phone | phone (alone) |
| emergency_contact | emergency_contact_name |
| emergency_phone_primary | emergency_contact_phone |
| allergies_details | allergy_details |
| can_self_administer_meds | can_self_administer |
| event_description | description (alone) |
| event_name | name (alone for events) |
| event_dates | dates (alone) |
| submitted_at | created_at (for submissions) |

### Date Formatting

- All displayed dates use `formatDate()` from `$lib/utils/formatDate.ts`
- Date-only values: "20 March 2026"
- Datetime values (with timestamp): "20 March 2026 at 6:29 pm"
- Date INPUT fields keep YYYY-MM-DD format (for `<input type="date">`)

### Notifications

- Use toast system (`toastSuccess`, `toastError` from `$lib/stores/toast`)
- Never use `alert()` — always use toasts
- Toasts pop in from top center with auto-dismiss

### Modals / Confirmations

- Use `ConfirmModal` component (`$lib/components/ConfirmModal.svelte`) for all destructive/confirmation actions
- Blurred backdrop (`backdrop-blur-sm`)
- Never use `confirm()` — always use ConfirmModal

### Navigation

- Nav items have active states (primary color + bottom border)
- Events link is active for any `/event/*` subpage
- Both desktop and mobile nav must be updated together

### Organizations

- Young Men: Deacons, Teachers, Priests
- Young Women: Builders of Faith, Messengers of Hope, Gatherers of Light (DB keys remain `beehives`, `mia_maids`, `laurels`)
- Stored as JSON array on events table
- Display uses `getOrgDisplayLabels()` — shows parent label when all children selected
- Color badges: blue (Young Men family), purple (Young Women family)

### Auth

**Server (online/hybrid):**
- JWT (HS256) in HttpOnly SameSite=Strict cookies, set by the Bun server (`server/src/lib/auth.ts`)
- `authMiddleware` populates `c.get('user')` on every request; `requireAuth` guards protected routes; admin routes additionally require `role === 'super'`
- The browser calls the server directly with `credentials: 'include'` — SvelteKit does not proxy auth (`hooks.server.ts` is a passthrough)

**Local mode:**
- SHA-256 password hashing via Web Crypto API
- Session stored in localStorage (device-level security)

### PDF Generation

- Uses pdf-lib to fill in the actual official church PDF form fields
- Template PDF at `server/src/templates/permission-form.pdf`
- Drawn signatures embedded as PNG images at field positions
- Typed signatures set as text in form fields
- Form is flattened after filling (fields become static)
- PDF generation runs in the Bun server process (`server/src/services/pdf.ts`)
- In local-only mode (incl. the desktop/mobile app) there is no server; the frontend generates PDFs client-side with pdf-lib (`frontend/src/lib/services/pdf.ts`)

### Database

**Single source of truth:** the data model is defined once in `shared/schema.ts`.
Run `bun run gen:schema` (from repo root) to regenerate:
- `server/src/schema.generated.ts` — server DDL (`bun:sqlite`), consumed by `server/src/db.ts`
- `frontend/src/lib/data/local/schema.generated.ts` — local DDL (sql.js), consumed by `local/schema.ts`
- `frontend/src/lib/data/sync/sync-columns.generated.ts` — per-collection sync column specs, consumed by `sync/manager.ts`

**Never edit the `*.generated.ts` files by hand.** Per-target differences (server-only
`must_change_password`; local-only `pending_changes`/`local_meta`/`blob_data`; the
`created_at`/`submitted_at` vs `created`/`updated` timestamp columns) are encoded via
`targets` flags in the descriptor. A guard test (`server/test/schema.test.ts`) fails if
the committed generated files drift from `shared/schema.ts`.

### Testing

- Server uses `bun test`; tests build the app in-process with an in-memory SQLite DB (`createDb(':memory:')`) and drive it via Hono's `app.request()` (see `server/test/`)
- No network/ports in tests — the same `app.fetch` handler the HTTP server uses
- Rate limiters skip in test env (`NODE_ENV=test`)
- `crypto.randomUUID()` for IDs
- Frontend tests use Vitest

## Route Mounting Order (Critical)

In `server/src/app.ts`, the PUBLIC form routes (`createFormRoutes`) MUST be mounted
BEFORE the authed events routes (`createEventRoutes`) — both live under `/api/events`.
They never collide on a path+method (form uses `/:id/form`, `/:id/submit`), but
mounting form first preserves the old semantics (e.g. public `GET /:id/attachments`).

1. Form routes (`/api/events` — public: `/:id/form`, `/:id/submit`, attachment reads)
2. Events routes (`/api/events` — authed CRUD + attachment writes)
3. Auth (`/api/auth`), Profiles (`/api/profiles`), Submissions (`/api/submissions` — `/mine` BEFORE `/:id/*`)
4. Groups (`/api/groups`), Invites (`/api/invites` — public token preview/accept), Admin (`/api/admin` — super only)
